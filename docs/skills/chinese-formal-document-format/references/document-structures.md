# Document type structures

Reference for the primary document types covered by this skill. Read the relevant section when formatting that type.

The structures below are **descriptive, not prescriptive**. If the user's draft is structured differently, format what is present. Do not reorganize the text.

---

## 报告 (Report)

A 报告 is an upward-facing document used to summarize work, report situations, or respond to inquiries. It is not used to request approval (that's 请示).

### Typical structure

1. **Title**: `关于XXXX工作的报告` or `XX年度XX工作报告` or `XX工作完成情况报告`
2. **Recipient** (optional): The receiving organization name + `：`
3. **Lead paragraph**: Brief context, e.g., `现将我公司2026年第一季度工作情况报告如下。`
4. **Body** with hierarchical headings:
   - `一、工作完成情况` (or similar)
   - `二、存在的问题` (or similar)
   - `三、下一步工作打算` (or similar)
5. **Closing phrase** (optional): `特此报告。`
6. **Signature**: Organization name
7. **Date**

### Special rules
- A 报告 must NOT contain request-for-approval language (`请批示` / `妥否请示`). If the user has such language, **point it out** but do not remove it.
- Reports may use bullet/numbered lists within sections; preserve them as-is.
- Reports often include numerical data; preserve all numbers exactly.

## 方案 (Plan / Proposal)

A 方案 is a forward-looking document that lays out how to accomplish something. It's used for project plans, implementation schemes, work plans, etc.

### Typical structure

1. **Title**: `XXXX工作方案` or `关于XXXX的实施方案`
2. **Lead paragraph** (optional): Background and objectives in compact form, possibly starting with `为深入贯彻……根据……特制定本方案。`
3. **Body** with hierarchical headings — commonly:
   - `一、总体要求` (or 指导思想 / 工作目标)
   - `二、主要任务` (or 重点工作 / 工作内容)
   - `三、实施步骤` (or 进度安排 / 时间安排)
   - `四、保障措施` (or 工作要求 / 组织保障)
4. **Signature** (optional in some orgs — sometimes the plan is internal-only and doesn't need署名)
5. **Date**

### Special rules
- Plans often have **timestamps in body** (e.g., `2026年6月底前`); preserve them.
- Plans may have **named responsible parties** (e.g., `（牵头部门：XXX）`); these are part of the body, format as 仿宋 3号 like surrounding text.
- Plans may end with appendices like 任务分工表; these are typically tables and are out of scope for typography (preserve as-is).

## 函件 (Letter / Function)

A 函 (or 函件) is used between peer-level organizations (平行机关) or between non-subordinate organizations (不相隶属机关) for inquiry, response, negotiation, or request-for-approval (of items that don't require an upward 请示).

### Typical structure

1. **Title**: `关于XXXX的函`
2. **Recipient (主送机关)**: The full name of the receiving organization + `：`
3. **Lead paragraph**: Brief context referencing prior communication or relationship, e.g., `根据贵我双方前期沟通……` / `贵公司XX函（XX字〔2026〕XX号）收悉。`
4. **Body**: Usually shorter than a 报告 — focused on the specific matter
5. **Closing phrase**: One of:
   - 商洽函: `特此函达，请研处。` / `以上事项，请研处函复为盼。`
   - 询问函: `特此函询，请函复。`
   - 答复函: `特此函复。`
6. **Contact info** (optional but common): `（联系人：XXX  电话：XXX-XXXXXXXX）`
7. **Signature**: Sender organization
8. **Date**

### Special rules
- 函件 are **平行行文** — language should not be subservient (avoid `请批示` / `恳请`) nor commanding (avoid `请按……执行`). Use 商洽 tone.
- If the user's draft has the wrong tone, point it out but don't rewrite.
- 函件 often use **vocative `贵`** when referring to the recipient (贵公司、贵单位); preserve these.

## 会议纪要 (Meeting Minutes)

会议纪要 record the proceedings and decisions of a meeting. Their structure is the most different from the other types.

### Typical structure

1. **Title**: `XXXX会议纪要` or `XX年XX月XX日XXXX会议纪要`
2. **Metadata block** (immediately after title) — this is unique to 会议纪要:
   ```
   会议时间：2026年5月13日 14:00-16:00
   会议地点：XX会议室
   主持人：XXX
   出席人员：XXX、XXX、XXX
   列席人员：XXX、XXX
   缺席人员：XXX（请假）
   记录人：XXX
   ```
3. **Body**:
   - `一、会议议题` (list of topics)
   - `二、议定事项` (decisions made — this is the most important section)
   - For each decision item:
     - State the decision clearly
     - Identify responsible party (`牵头：XXX部门 / 配合：XXX部门`)
     - Set deadline (`完成时限：2026年X月X日前`)
3. **Signature** (optional): The body that convened the meeting, e.g., `XX公司办公室`
4. **Date**: The date the meeting minutes are issued (may differ from meeting date)

### Special formatting for the metadata block

The metadata block (会议时间/地点/主持人 etc.) is structured data, not body prose. Format it as:
- Font: 仿宋_GB2312 3号
- Alignment: Left
- **No first-line indent** (unlike body text)
- Each item on its own line

You may also format it as a 2-column table for readability, but a series of left-aligned lines is more traditional and acceptable.

### Special rules
- 议定事项 are often numbered with hierarchical headings (`一、` per topic, then `1.` per sub-decision). Format them per the standard heading hierarchy.
- In meeting minutes, a numbered full sentence such as `1. 由市场部牵头，于10月25日前完成任务。` is still body text. Apply level-3 heading typography only to a short standalone label such as `1. 责任分工`.
- 会议纪要 use **declarative past tense** (`会议决定……` / `会议同意……` / `会议要求……`). If the user's text uses 命令式 or 第一人称, point it out but don't rewrite.
- Meeting minutes typically do **not** use the formal closing phrases (`特此报告` etc.).

## Cross-cutting guidance

### When the user's draft mixes elements from multiple types

Sometimes a user will write something that's "a 报告 with a 方案 attached" or "a 函 with meeting decisions". In these cases:

1. Identify the **primary** type (the framing of the document)
2. Apply primary type's structure to the overall
3. Treat embedded content as body — apply the heading hierarchy as written

Don't try to extract or reorganize. The user wrote what they wrote for a reason.

### When the user's draft is missing standard elements

Common omissions:
- No closing phrase (no `特此报告` etc.) → Leave as-is. Many internal documents omit these.
- No signature → If the document is clearly internal/draft, leave as-is. If it looks like a final outgoing document, ASK the user.
- No date → ASK the user. Date is essential for most public documents.
- No title → ASK the user. Title is essential.

### When the user's draft has typos or inconsistent terminology

POINT THEM OUT in a brief note after formatting, but DO NOT fix them. The user may have specific reasons for the wording.

## Other document types

The formatter also accepts `通知`, `请示`, `批复`, `意见`, `决定`, `通报`, `简报`, and general internal documents because the typography mechanics are shared. Their rhetorical structure is not standardized by this skill.

Use this fallback:

1. Treat the first non-empty line as the title unless the user identifies a different line.
2. Preserve the recipient, body, attachments, signature, and date in their original order.
3. Apply heading styles by the numbering pattern already present.
4. Use `generic` when the title and structure do not identify one of the four primary types.
5. Point out content-level concerns without rewriting them.

### 通知

Typical elements are a title, recipient, notification body, action or deadline, signature, and date. Do not add or remove action language.

### 请示

Typical elements are a title, one recipient, one matter, a request, and a closing request phrase. If the draft contains several unrelated matters, report the “一文一事” concern but preserve the content.

### 批复

Typical elements are a title, recipient, response to the prior request, a decision, and a date. Preserve any quoted document number and the exact decision language.

### 其他材料

For internal analysis, briefing, work summary, research note, or leadership speech drafts, use the same title/heading/body/signature typography only when the user asked for the formal-document style. Do not treat a speech or briefing as an official outgoing document merely because it has headings.
