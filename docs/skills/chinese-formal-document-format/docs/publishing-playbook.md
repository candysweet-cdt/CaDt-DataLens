# 发布与自媒体运营手册

> 品牌署名：鼓翼成长星球

## 结论

不要只在 GitHub 发布，也不要把“让用户去 GitHub”当作唯一入口。

建议采用四层结构：

1. **代码主仓**：GitHub；
2. **国内镜像**：Gitee；
3. **官方生态**：OpenAI 通用插件目录（将 Skill 包成 skills-only 插件后提交）；
4. **自有落地页/内容入口**：B站、视频号、小红书、抖音、微信公众号。

核心原则：**内容平台负责让人看见，国内落地点负责让人下载，GitHub/Gitee 负责版本与源码可信度。**

## 一、Skill 发布到哪里

### GitHub：主仓库和版本档案

适合：

- 保存源码、Issue、版本标签和 Release；
- 给技术用户完整安装说明；
- 用 Actions 自动测试；
- 每次发布上传 `.skill`、`.zip` 和 SHA-256。

建议仓库结构：

```text
chinese-formal-document-format/
├── SKILL.md
├── README.md
├── VERSION
├── CHANGELOG.md
├── docs/
│   ├── iterations.md
│   └── publishing-playbook.md
├── scripts/
├── profiles/
├── examples/
└── tests/
```

### Gitee：中国大陆镜像

适合：

- 为无法稳定访问 GitHub 的用户提供源码和 Release 下载；
- 同步 README、版本说明和安装包；
- 在视频/文章中给国内用户直接入口。

建议做法：

- GitHub 为主仓，Gitee 为镜像；
- 每个版本同步 tag 和 Release；
- 两边都放 `.skill`、`.zip`、更新日志、SHA-256；
- 国内视频只引导到 Gitee 或你自己的国内下载页。

### OpenAI 通用插件目录

如果希望 ChatGPT 和 Codex 用户能搜索、安装和更新，需要把 Skill 包成 **skills-only plugin**：

```text
chinese-formal-document-format/
├── .codex-plugin/
│   └── plugin.json
└── skills/
    └── chinese-formal-document-format/
        ├── SKILL.md
        ├── scripts/
        └── ...
```

官方流程：

1. 在 OpenAI Platform 完成个人或企业身份验证；
2. 打开 Plugins 提交页，上传完整 plugin ZIP；
3. 处理 Metadata / Skills 自动检查；
4. 提交审核；
5. 通过后选择发布时间；
6. 发布后用户可通过目录直链或精确名称搜索找到。

OpenAI 官方说明：ChatGPT 和 Codex 共用通用插件目录，但发布后的普通目录曝光有限，增强推荐位置不能由开发者主动申请。

参考：

- https://developers.openai.com/plugins/concepts/plugins
- https://developers.openai.com/plugins/deploy/submission

注意：单独的 `.skill` 适合手动安装；要进入官方目录，需要按官方要求改造成 plugin ZIP。Skill 里的脚本在网页端是否执行，取决于安装环境；本 Skill 的完整能力最好在 Codex Desktop 或本地 Python 环境演示。

### 国内自有下载页

这是最重要的“防失联入口”。

建议使用：

- 阿里云 OSS / 腾讯云 COS 存放 `.skill`、`.zip` 和示例；
- 一个简单静态页展示下载、版本、安装、更新和演示；
- 微信公众号文章放二维码，而不是把所有安装包直接塞进正文；
- B站简介、小红书主页和视频号/抖音主页统一指向同一个短链或二维码。

下载页最少包含：

- 一句话用途；
- 支持的文件类型；
- 最新版本；
- macOS / Windows 安装；
- 30 秒演示；
- 已知限制；
- 更新日志；
- 隐私和安全说明；
- GitHub / Gitee 镜像。

不要把网盘链接作为唯一入口：链接容易失效，也无法形成可搜索、可追踪的产品主页。

## 二、四个平台怎么分工

### B站：完整教程与信任

内容：

- 5–8 分钟完整演示；
- 从混乱 DOCX 到核验报告的完整流程；
- 解释为什么“编号不等于标题”；
- 展示测试报告、版本历史和安装步骤。

目标：收藏、关注、建立技术可信度。

### 抖音/视频号：30 秒钩子

前 3 秒直接展示冲突：

> AI 把普通编号当成了三级标题，问题出在哪？

接着：

1. 展示错误；
2. 展示修正版；
3. 展示“正文与关键结构一致”；
4. 引导评论关键词或主页下载。

目标：让陌生用户看懂“这能解决什么具体问题”。

### 小红书：搜索型图文教程

建议 6–9 张图：

1. 封面：一句话结果；
2. 排版前；
3. 排版后；
4. 一级/二级/三级标题识别；
5. 编号正文的正确判断；
6. 核验报告；
7. 安装步骤；
8. 适用和不适用场景；
9. 获取方式和版本更新。

目标：搜索、收藏和长期长尾流量。

### 微信公众号：长期可搜索的总部

每个版本发一篇：

- 为什么做；
- 这版改了什么；
- 前后对比；
- 安装路径；
- 下一版计划；
- 扫码下载。

适合承接 B站/视频号里的深度用户，也方便别人转发到微信群。

## 三、一个内容，四个版本

每次迭代只做一份“母内容”，然后拆分：

| 平台 | 时长/形式 | 核心目标 |
|---|---|---|
| B站 | 5–8 分钟实操 | 信任与收藏 |
| 抖音/视频号 | 30–45 秒冲突示范 | 触达与评论 |
| 小红书 | 6–9 图流程卡 | 搜索与收藏 |
| 公众号 | 长文与下载入口 | 承接、搜索、更新通知 |

不要为四个平台分别发明四套叙事。保持同一个产品名、同一张前后对比图和同一个下载入口。

## 四、首月内容节奏

### 第 1 周：发布

- “只改格式，不改一个字”；
- 30 秒前后对比；
- 5 分钟完整教程；
- 小红书安装卡；
- 公众号发布文章。

### 第 2 周：讲问题

- “为什么 AI 会把 1. 后面的一整句话加粗？”；
- 黑白名单与正文完整性；
- 用户最担心的“乱改内容”。

### 第 3 周：讲场景

- 报告排版；
- 会议纪要；
- 方案与表格；
- 单位自定义字体和页边距。

### 第 4 周：讲版本和可信度

- 0.9 → 1.0 → 1.1 的进化；
- 每次发布如何测试；
- 公开更新日志；
- 征集真实脱敏文档做下一版测试。

## 五、关注与转化设计

每个视频只保留一个主行动：

> 评论区回复“排版”，获取 Skill、示例文件和安装说明。

执行细节：

- 主页置顶“下载 + 更新日志”；
- 评论置顶同一条获取方式；
- 视频最后 5 秒固定二维码/短链；
- 每次新版本在四个平台同步“更新了什么”；
- 收集用户最常问的三个问题，直接做下一期；
- 让用户带着脱敏场景来，而不是只做“点赞抽奖”；
- 用真实前后对比、核验报告和失败边界建立专业感。

## 六、推荐的第一版落地组合

1. GitHub 建主仓并打 tag；
2. Gitee 建镜像；
3. 做一个国内下载页；
4. 把 Skill 包成 skills-only plugin，尝试提交 OpenAI 通用目录；
5. B站发完整教程；
6. 抖音/视频号发 30 秒冲突示范；
7. 小红书发 9 图安装与案例；
8. 公众号发长文，承载二维码和更新记录。

先跑通这套闭环，再考虑付费、会员、私域群或更多平台。目标是让用户完成：**看到问题 → 相信结果 → 下载成功 → 回来反馈 → 关注下一版**。
