# 版本与迭代记录

当前版本：**1.3.0**

版本记录同时保存在三处：

1. `CHANGELOG.md`：面向用户的变化说明；
2. 本文件：每次迭代的目标、改动、验证和兼容性；
3. Git tag / Release：保存每个版本的可下载快照和安装包。

新的发布包只携带最新版；旧版本应在 GitHub、Gitee 或自有下载页保留，不要全部塞进当前 Skill。

## 0.9.0 前史：未正式编号的迭代

说明：下面这些阶段是依据本地文件创建时间、修改时间、脚本内容和 Skill 快照差异重建的。它们在当时没有正式 `0.x` 版本号，因此不能把“0.1、0.5”之类写成官方历史；本文件只把它们作为研发里程碑保存。

### 前史 A：2026-08-10，单篇生成器

证据：`2026-08-10/ni/work/build_soe_feedback_docx.py`。

内容：

- 为一个“十五五”规划反馈意见直接生成 Word；
- 首次落实 A4 页面、37/35/28/26 mm 页边距；
- 使用方正小标宋简体二号标题、黑体一级、楷体二级、仿宋正文；
- 固定 28 磅行距、2 字符首行缩进、右对齐落款与日期；
- 同日进行了两轮渲染，`render_soe` 为 7 页，`render_soe2` 为 10 页。

意义：这是“国企公文排版”从手工操作转为脚本生成的第一份可追溯证据，但仍是为单篇文档写死的生成器。

### 前史 B：2026-08-11，Skill 骨架

证据：Skill 目录下 `SKILL.md`、`README.md`、3 份参考文档和 4 个模板的创建时间均为 17:22。

内容：

- 正式建立 `soe-document-format` Skill 目录；
- 固化报告、方案、函件、会议纪要四种文种；
- 增加格式规范、文种结构、保守模式参考；
- 制作四份可复用 DOCX 模板；
- 核心承诺确定为“只改格式，不改文字”。

限制：当时仍没有通用排版脚本，主要依赖 Agent 按说明操作。

### 前史 C：2026-08-21，真实采购文件实战

证据：`2026-08-21/soe-document-format-users-ianlink-codex/work/format_docx.py`、`update_toc.py` 与采购邀请文件输出。

内容：

- 第一次在真实大型国企文件上跑完整排版；
- 处理封面标题、单位名称、日期、目录、正文和表格；
- 增加固定分页、目录页码回填、表格四号和单倍行距；
- 删除原文档中可能干扰渲染的未定义样式引用、书签和目录级别；
- 生成 22 KB DOCX 和对应的 PDF 验证文件。

意义：这一轮暴露并解决了“目录页码、封面分页、表格、未定义样式”等实际文档问题，已经明显超出 8 月 10 日的单篇脚本。

### 前史 D：2026-08-26，通用 DOCX 构建器

证据：`2026-08-26/cavas/work/build_soe_docx.py`，创建于 11:32。

内容：

- 从 Markdown 读取内容并构建 DOCX，不再写死单篇正文；
- 支持标题、主送机关、正文层级、表格、落款和日期；
- 显式设置表格宽度和单元格对齐；
- 支持 `（一）标题。正文……` 同段双 run：标题楷体、正文仿宋。

意义：这是从“为某篇文档写脚本”走向“通用排版器”的转折。

### 前史 E：2026-08-26，Skill 快照与规则整合

证据：`soe-skill-snapshot` 创建于 11:48；随后 11:49 原 Skill 的 `SKILL.md` 和 `format-spec.md` 被更新。

新增内容：

- `SKILL.md` 新增 Codex 桌面/CLI 的实际生成流程；
- 明确输出 `.docx`；
- 新增同段“二级标题 + 正文”的双 run 规则；
- 新增表格标题、表头、字号、边框和列宽规范。

这一状态在本次历史整理中回填为 **0.9.0**，表示“规则、模板和实战经验已经合并成可复用版本”。

## 0.9.0：规则型起点

目标：把国企材料排版经验固化成可复用规则。

内容：

- 定义 GB/T 9704 参考版式和保守编辑边界；
- 覆盖报告、方案、函件、会议纪要；
- 提供 3 份规范参考和 4 个 DOCX 模板；
- 强调只改格式、不改文字。

当时限制：

- 主要依赖模型直接编辑 DOCX；
- 没有确定性排版脚本；
- 没有独立核验报告；
- README 偏 Claude 使用场景；
- 没有组织级 profile。

- 技术名：`chinese-formal-document-format`；
- 默认规则继续参照 GB/T 9704；
- 覆盖公文及组织内部正式材料；
- 同步更新模块、测试、示例、报告和发布包。

## 后续版本规则

- 修 bug：递增补丁号，如 `1.1.2`；
- 增加向后兼容能力：递增次版本号，如 `1.2.0`；
- 改技术名、目录结构或核心行为：递增主版本号，如 `2.0.0`；
- 每次发布必须同时更新 `VERSION`、`CHANGELOG.md`、本文件、测试和发布包；
- 发布后创建 Git tag `vX.Y.Z`，并上传 `.skill`、`.zip`、SHA-256 和发布说明。
